# 설계 결정서 — 기획서가 정하지 않은 것들

> 기준 문서: [`SPEC-EMAIL-TICKET.md`](SPEC-EMAIL-TICKET.md)
> 이 문서는 기획서를 **대체하지 않습니다.** 구현에 필요하지만 기획서에 명시가 없어
> 개발 과정에서 확정한 사항만 기록합니다. 기획서와 충돌하면 기획서가 우선입니다.

## 1. 확정한 상수

### 1.1 상태 파이프라인 (기획서 3.2)

| 코드값 | 화면 표기 | 의미 |
|---|---|---|
| `intake` | 접수 대기 | 에이전트가 적재한 직후 |
| `triage` | Triage | 담당자 배정·내용 보완 단계 |
| `in_progress` | 진행 중 | 개발 착수 |
| `testing` | 테스트 | 검증 |
| `deploy` | 배포 | 운영 반영 |
| `done` | 완료 | 종료. 회신 발송 대상 |

DB에는 **영문 코드값**을 저장하고 한글은 화면에서만 매핑합니다. 라벨을 바꾸고 싶을 때 DB 마이그레이션이 필요 없습니다.

전이는 **인접 단계 이동과 되돌리기만** 허용하며, 관리자는 임의 단계로 점프할 수 있습니다.
전이가 일어날 때마다 `ticket_status_history`에 한 행이 남습니다 — 리드타임 통계의 원천입니다.

### 1.2 장애 등급 (기획서 3.1)

`critical` 매우심각 · `high` 높음 · `medium` 보통 · `low` 낮음

### 1.3 대분류 (2026-08-06 확정)

| 코드값 | 표기 | 기준 | 누가 정하나 |
|---|---|---|---|
| `incident` | 장애 | 동작하던 것이 멈춤·오작동 | LLM 자동 |
| `maintenance` | 유지보수 | 단순 수정·개선 | LLM 자동 |
| `development` | 신규개발 | **공수 1주일 이상** | **관리자 수동 승격** |

라이프사이클 6단계는 셋 다 동일하고, 관리 방식만 갈립니다 —
MTTR은 장애, 주간 현황은 유지보수, Gantt는 신규개발.

**LLM은 앞의 둘만 고릅니다.** 공수 판단에 필요한 정보가 메일에 없기 때문입니다.
승격 시점은 `ticket_meta.promoted_at`에 남아 "접수 후 며칠 만에 프로젝트가 됐는지"를 답합니다.

### 1.4 중분류

`error` 오류 · `improve` 개선 · `fix` 수정 · `new` 신규

기획서 2번의 "오류/개선/수정/신규"입니다. 대분류가 생기면서 한 단계 아래로 내려왔고,
"개선 요청이 몇 건인지" 같은 통계를 위해 남겼습니다.

### 1.5 시스템 구분 — 하드코딩하지 않습니다 (2026-08-06 변경)

`public.systems` 등록표를 운영자가 설정 화면에서 관리합니다. **초기값 없이 빈 상태로 시작**합니다.

| 결정 | 이유 |
|---|---|
| `ticket_meta.system_type`에 **외래키를 걸지 않음** | 시스템을 목록에서 지웠다고 과거 티켓의 분류가 사라지면 안 됩니다. 등록표에 없는 코드는 화면에서 '미분류'로 보이되, 툴팁에 원래 코드를 남깁니다 |
| `null` 허용 | 미분류를 표현해야 합니다. **없는 값을 지어내지 않습니다** |
| 등록된 시스템이 0개면 LLM 스키마에서 `system_type` **항목 자체를 제거** | 빈 enum은 스키마 위반이고, 억지로 기본값을 넣으면 없는 분류가 생깁니다 |
| 각 시스템의 `description`을 프롬프트에 포함 | LLM이 무엇을 근거로 고를지 운영자가 정합니다 |

### 1.6 접수 판정 기준 — 설정으로 뺐습니다 (2026-08-06 변경)

"무엇을 요청 메일로 볼 것인가"가 프롬프트 문자열에 박혀 있었습니다.
운영자는 기준을 볼 수도, 고칠 수도 없었고, LLM이 걸러낸 메일은 흔적조차 남지 않았습니다.

- `intake_rules` — 접수/제외 기준. 기존 코드의 기준 7줄이 초기값
- `intake_rule_history` — 변경 이력. "언제부터 판정이 달라졌는지" 추적
- `app_settings.intake_ambiguous_policy` — 애매할 때의 편향 (기본 `include`)
- `scanned_mails` — **스캔한 메일 전부.** 티켓이 안 된 것도 판정 근거와 함께 보관

DB를 못 읽으면 코드의 기본 기준으로 넘어갑니다. **근거 없이 판정하게 두지 않습니다.**

## 2. 기획서 4번 스키마에서 더한 것과 그 이유

기획서의 5개 테이블을 그대로 두되, 다음을 추가했습니다. **모두 기획서 본문이 요구하는 기능을 위한 것입니다.**

| 추가 | 근거 |
|---|---|
| `tickets.source_message_id` (unique) | 에이전트가 "주기적으로 스캔"(2-1)하므로 같은 메일을 두 번 읽습니다. 아웃룩 `EntryID` 기준 유일 제약이 없으면 스캔할 때마다 티켓이 복제됩니다 |
| `tickets.received_at` | 카드에 "최초 접수일"(3.2)을 표시해야 하는데, DB `created_at`은 에이전트가 적재한 시각이라 메일 수신일시와 다릅니다. 주말에 온 메일이 월요일 접수로 보이면 안 됩니다 |
| `ticket_status_history` | "라이프사이클 통계"(1)와 "처리 리드타임"(3.2). 완료 시각 하나만으로는 어느 단계에서 막혔는지 알 수 없습니다 |
| `outbound_emails` | "웹에서 발송 요청 ➔ 에이전트가 감지"(2-5). 티켓 상태만 보고 발송하면 재시도·취소·중복발송 이력이 남지 않습니다. 발송은 되돌릴 수 없으므로 큐를 별도 테이블로 둡니다 |
| `users.is_active` | 퇴사자 계정을 지우면 `comments.user_id`가 함께 사라집니다. 비활성 처리로 이력을 보존합니다 |

### 2.1 `users` 테이블과 Supabase Auth의 관계

`public.users.id`는 `auth.users.id`를 그대로 참조합니다. 인증은 Supabase Auth가, 역할(`role`)과 표시 이름은 `public.users`가 담당합니다.
가입 시 트리거가 `public.users` 행을 자동 생성하며 **기본 역할은 `member`** 입니다. 관리자 승격은 SQL 또는 관리자 화면에서만 가능합니다.

## 3. 권한 설계 (기획서 3.2)

| 대상 | 관리자(admin) | 팀원(member) |
|---|---|---|
| 티켓 조회 | 전체 | 전체 |
| 티켓 상태 변경 | 전체 | **본인에게 할당된 건만** |
| 담당자 배정 | O | X |
| 티켓 내용 보완 | O | 본인 할당 건만 |
| 코멘트 | O | O (본인 것만 수정·삭제) |
| 첨부 추가·삭제 | O | X |
| 회신 발송 요청 | O | X |
| 티켓 삭제 | O | X |
| 사용자 역할 변경 | O | X |

DB 레벨 RLS로 강제합니다. 화면에서 버튼을 숨기는 것은 편의일 뿐이고, 실제 차단은 정책이 합니다.

### 3.1 키 사용 원칙

| 실행 주체 | 키 | 이유 |
|---|---|---|
| 웹 대시보드(브라우저) | **Publishable(anon) 키** | 공개돼도 RLS가 막습니다 |
| Local PC 에이전트 | **Service role 키** | 로그인 세션 없이 적재해야 하고, 브라우저에 노출되지 않는 로컬 프로세스입니다 |

**Service role 키는 웹 코드·저장소·환경변수 어디에도 들어가지 않습니다.** 에이전트 PC의 `.env` 한 곳에만 존재합니다.

## 4. 에이전트 설계

### 4.1 실행 환경

에이전트는 **Windows + Outlook 데스크톱**에서만 실제 동작합니다(`pywin32` COM). 개발·테스트는 macOS에서 이뤄지므로,
Outlook 접근을 `MailClient` 인터페이스로 감싸고 두 구현을 둡니다.

| 구현 | 용도 |
|---|---|
| `OutlookMailClient` | 운영. `win32com.client` 사용 |
| `FixtureMailClient` | 개발·테스트. `fixtures/*.json`의 메일을 읽고 발송은 파일로 기록 |

플랫폼 판별로 자동 선택하며 `AGENT_MAIL_BACKEND=fixture`로 강제할 수 있습니다.
**집계·분류·요약 로직은 전부 순수 함수**이며 Outlook 없이 단위 테스트가 돕니다.

### 4.2 LLM 파이프라인

기획서 3.1의 1차/2차 판별을 **한 번의 호출**로 처리합니다. 두 번 부르면 비용과 지연이 두 배인데,
1차에서 T가 나오면 어차피 같은 본문을 다시 읽기 때문입니다. 응답 스키마에 `is_request`(1차)와
나머지 필드(2차)를 함께 두고, `is_request=false`면 나머지를 무시합니다.

> **기획서와 다른 점 — LLM 제공자**
> 기획서 5장은 "Claude API로 분류"라고 적었지만, **Google Gemini를 씁니다.**
> 운영 주체가 Gemini 키를 제공하기로 했기 때문입니다 (2026-08-06 결정).
> 판별 로직·프롬프트·예외 처리 방침은 기획서 3.1 그대로이고, 호출 대상만 다릅니다.

- 모델: `gemini-2.5-flash` (`GEMINI_MODEL`로 변경 가능)
- 구조화 출력: `response_mime_type=application/json` + `response_json_schema` — 자유 텍스트 파싱을 하지 않습니다
- `temperature=0` — 같은 메일은 같은 결과가 나와야 합니다
- 본문은 12,000자로 절단하고 인용부(`-----Original Message-----` 이하)를 제거한 뒤 전달합니다
- **판별 실패·API 오류·안전 필터는 티켓을 버리지 않습니다.** `etc`/`medium`/`triage`로 적재하고 `llm_error`에 사유를 남깁니다

**Gemini 스키마 제약** — 두 가지를 지켜야 요청이 거절되지 않습니다.

| 제약 | 대응 |
|---|---|
| union 타입(`["string","null"]`) 미지원 | `due_date`를 `string`으로 받고 **없으면 빈 문자열**. 파서가 `None`으로 바꿉니다 |
| `additionalProperties` 미지원 | 스키마에서 제거. 대신 파서가 아는 키만 읽고 나머지는 무시합니다 |

**교체 지점은 `Classifier` 클래스 하나입니다.** `parse_response` / `_fallback` /
`build_user_message`는 제공자와 무관해서, 나중에 다른 모델로 옮겨도 판별 규칙과 테스트가 그대로 남습니다.

**시스템 종류는 인자로 받습니다.** `build_response_schema(system_types)` /
`build_system_prompt(system_types)` 형태라, 시스템 종류가 설정 테이블로 옮겨갈 때
DB 값을 그대로 넘기면 됩니다. 지금은 상수를 기본값으로 씁니다.

### 4.3 회신 발송

기획서 5-4가 명시한 대로 **곧바로 보내지 않고 `Display()`로 아웃룩 창을 띄웁니다.** 사람이 눈으로 확인하고 보냅니다.
`AGENT_SEND_MODE=send`로 바꾸면 자동 발송하지만 기본값은 `display`입니다.

발송 큐 처리는 폴링(기본 30초)입니다. Realtime을 쓰면 에이전트 재시작 중 발생한 요청을 놓치므로,
"큐에 남아 있는 것을 처리"하는 폴링이 이 용도에는 더 안전합니다.

- Vite + React + TypeScript + Tailwind + React Router(**HashRouter**) + TanStack Query

- 컴포넌트는 `supabase` 클라이언트를 직접 부르지 않고 `src/lib/api.ts`만 경유합니다

## 6. 이 설계가 지키는 것

1. **메일 한 통이 두 번 티켓이 되지 않는다** — `source_message_id` 유일 제약
2. **내용이 부실해도 버리지 않는다** — 기획서 3.1 예외 처리를 코드 경로로 보장
3. **회신은 사람이 확인하고 보낸다** — 기본 `display` 모드
4. **service_role 키는 브라우저에 도달하지 않는다** — 웹은 anon 키만
5. **권한은 화면이 아니라 DB가 막는다** — RLS 정책

## 7. 수동 등록 — 왜 웹이 아니라 에이전트가 분류하는가 (2026-08-06)

메일로 오지 않은 요청(구두·전화·메신저)을 등록하는 경로입니다.
사용자 요구는 **"본문을 붙여넣으면 시스템이 성격을 판단해 티켓으로 등록"** 이었습니다.

여기서 갈리는 지점은 *누가 LLM 을 부르는가* 입니다.

| 방식 | 즉시성 | 대가 |
|---|---|---|
| 웹이 직접 호출 | 즉시 | **LLM API 키가 브라우저에 노출됩니다.** 정적 사이트라 번들에 그대로 들어갑니다 |
| Supabase Edge Function | 즉시 | 배포 대상이 하나 늘고 키를 Supabase 에도 둬야 합니다 |
| **에이전트 큐 (채택)** | 폴링 주기만큼 지연 | 새 구조 없음. 키가 에이전트 PC 한 곳에 유지됩니다 |

회신 발송 큐(`outbound_emails`)와 **같은 구조**라 새로 배울 것도, 배포할 것도 없습니다.
대가는 등록 후 최대 폴링 주기(기본 30초)의 지연인데, 에이전트는 어차피 그 PC 에서
상시 실행이라 실무상 문제되지 않습니다. 즉시성이 필요해지면 Edge Function 을
나중에 덧붙일 수 있고, 그때 이 경로를 버릴 필요도 없습니다.

### 7.1 수동 등록은 `is_request` 판정을 하지 않습니다

메일 수집과 결정적으로 다른 점입니다.

**사람이 직접 등록한 이상 "요청인가" 는 이미 답이 나온 질문입니다.** LLM 이
"일상 대화로 보인다" 고 판단해도 티켓을 만듭니다. LLM 의 몫은 분류
(대분류·등급·시스템·기한·제목)뿐입니다.

이걸 지키지 않으면 등록한 사람은 티켓이 생긴 줄 알고 있는데 실제로는
아무것도 없는 상황이 생깁니다. 등록 화면에 처리 상태(대기/생성됨/실패)를
함께 보여주는 것도 같은 이유입니다.

### 7.2 요청자 메일은 선택값입니다

구두 요청은 요청자 메일 주소를 모르는 경우가 흔합니다. 필수로 두면
아무 값이나 넣게 되고, 그러면 완료 회신이 엉뚱한 곳으로 갑니다.
비워 두면 `unknown@unknown` 으로 적재되고, 회신을 보내려 할 때
관리자가 주소를 채우게 됩니다.

## 8. 주간 현황 — 엑셀 출력 (2026-08-06)

요구는 **"리스트를 작업별로 엑셀로 출력하는 수준"** 이었습니다. 화면에서 표로 보고,
필요하면 `.xlsx` 로 내려받습니다.

### 8.1 신규개발은 뺍니다

주간 현황은 **상시 업무(장애·유지보수)의 진척**을 팀이 공유하는 자리입니다.
신규개발은 주 단위가 아니라 일정 단위로 봐야 하고, 섞으면 "이번 주에 안 끝난 건"
목록에 몇 달짜리 과제가 계속 올라옵니다. 신규개발은 Gantt 로 따로 봅니다.

### 8.2 구분 세 가지가 있어야 "주간" 입니다

같은 목록도 이게 없으면 그냥 전체 리스트입니다.

| 구분 | 조건 |
|---|---|
| 금주 완료 | 완료 시각이 이번 주 안 |
| 금주 접수 | 접수 시각이 이번 주 안 |
| 진행 중 | 그 외 — **이월된 건.** 접수가 몇 달 전이어도 아직 안 끝났으면 올라옵니다 |

이월 건을 빼면 "지난달부터 미뤄진 작업" 이 보고에서 사라집니다.

### 8.3 exceljs 는 동적 import 합니다

라이브러리가 940KB 라 정적으로 넣으면 보드·통계처럼 **매일 여는 화면**의 첫 로딩이
그만큼 느려집니다. 내려받기를 누를 때만 로드하도록 `await import('exceljs')` 로 두어
별도 청크로 분리했습니다 (본 번들 587KB / exceljs 청크 940KB).

행을 만드는 부분은 전부 순수 함수(`buildWeeklyRows`)이고 라이브러리와 무관합니다.
엑셀을 CSV 나 다른 형식으로 바꿔도 그 부분은 그대로 남습니다.

## 9. Gantt — 신규개발 일정 (2026-08-06)

### 왜 신규개발만 올리는가

`work_type = 'development'` 인 건만 대상입니다. 장애·유지보수는 보통 며칠 안에
끝나서 몇 달짜리 타임라인에 올리면 선 하나로 뭉개집니다. 100건을 그려도 아무것도
읽히지 않습니다. 그쪽은 주간 현황(8장)과 통계로 봅니다.

신규개발로 올리는 판단은 **사람**이 합니다 (관리자, 공수 1주일 이상 기준).
LLM 은 `incident` / `maintenance` 만 판정하고 `development` 는 내놓지 않습니다.

### 진척률은 상태에서 유도한 값입니다

퍼센트를 따로 입력받지 않습니다. 상태를 환산합니다:

| Intake | Triage | In Progress | Testing | Deploy | Done |
|---|---|---|---|---|---|
| 0% | 10% | 40% | 70% | 90% | 100% |

입력란을 하나 더 만들면 아무도 갱신하지 않아 늘 틀린 숫자가 남습니다. 상태는
어차피 바꾸므로 거기서 끌어오는 편이 실제와 덜 어긋납니다. 대신 **화면에 그
사실을 밝힙니다** — "진척률은 상태에서 유도한 값입니다" 범례가 항상 붙습니다.
안 밝히면 보는 사람은 담당자가 입력한 실측치로 읽습니다.

### 없는 일정은 지어내지 않습니다

구간을 정하는 순서 (`resolveSpan`):

1. `planned_start_date` + `planned_end_date` 가 둘 다 있으면 → 그대로 (실선)
2. 한쪽이라도 비면 → 빈 쪽을 `received_at` / `due_date` 로 메움 (점선 테두리 + 회색)
3. 시작·종료를 어느 쪽으로도 알 수 없으면 → **막대를 그리지 않고** '일정 미정'
   목록으로 뺌

3번이 핵심입니다. "오늘부터 2주" 같은 기본값을 넣으면 화면은 채워지지만 보는
사람은 그게 실제 계획인 줄 압니다. 계획이 없다는 사실 자체가 정보입니다.

2번도 회색 + 점선으로 구분하고, 몇 건이 그런지 화면에 숫자로 적습니다.

### 색

데이터를 나르는 색은 두 개뿐입니다 — 진척 `#2a78d6`, 기한 초과 `#c0392b`.
CVD 검증을 통과했습니다 (protan ΔE 26.1, 일반시야 31.2). 계획 미입력의 회색
`#cbd5e1` 은 채도가 없어 검증 대상이 아니고, 점선 테두리와 범례로 따로
구분합니다 — 색만으로 뜻을 나르지 않습니다.

빨강이 '기한 초과 막대' 와 '오늘 선' 두 곳에 쓰이므로 범례에 둘 다 적었습니다.

### 축

데이터 범위 양옆에 3일씩 여백을 두고, **오늘이 범위 밖이면 축을 늘려 넣습니다**.
오늘 선이 안 보이면 지연을 읽을 수 없기 때문입니다.

### 순수 함수 경계

`web/src/lib/gantt.ts` 는 좌표(%)까지 전부 계산해 내놓고, `GanttPage.tsx` 는
그 숫자를 그리기만 합니다. 그래서 19개 단위 테스트로 경계 조건(막대가 축을
벗어나지 않는지, 하루짜리도 보이는지, 종료가 시작보다 빠른 경우)을 전부
검증할 수 있습니다.

## 10. 상태 모델 — 보류와 종료 방식, 그리고 영어 라벨 (2026-08-06)

> ### ⚠ 기획서와 다른 부분 (운영자 승인)
>
> `docs/SPEC-EMAIL-TICKET.md` 3.2 는 파이프라인을 이렇게 정합니다:
>
> `[접수 대기] ➔ [분석/할당] ➔ [진행 중] ➔ [테스트] ➔ [배포] ➔ [완료]`
>
> 여기서 두 가지가 달라집니다.
>
> 1. **보류(On Hold)가 추가**되어 상태가 7개입니다. 기획서의 6단계는 그대로
>    `PIPELINE_STATUSES` 로 남아 있고, 보류는 그 옆길입니다.
> 2. **화면 라벨이 영어**입니다. 저장값은 기획서와 동일한 영어 코드값이고,
>    요청자에게 나가는 회신 메일은 기획서대로 한국어를 씁니다.
>
> 기획서가 정본이라는 규칙(CLAUDE.md)에 대한 예외이며, 2026-08-06 에
> 운영자가 명시적으로 결정했습니다. 기획서를 갱신하실 때 이 절을 지우세요.


### 왜 Jira 를 베끼지 않았는가

"Jira 표준" 이라는 단일한 것이 없습니다 — Service Management 기본값,
Software 기본값, ITIL 계열이 다 다릅니다. 베낄 가치가 있는 건 상태 목록이
아니라 원칙 하나입니다: **상태와 종료 방식은 다른 필드다.**

상태는 "지금 누가 무엇을 하고 있는가", 종료 방식은 "어떻게 끝났는가" 입니다.

### 상태에 자격을 주는 기준

**다른 사람이, 다른 것을 기다리고 있는가.** 같은 사람이 같은 걸 기다리면
그건 상태가 아니라 필드나 필터입니다.

이 기준으로 두 가지를 결정했습니다.

**'분석/할당' 을 쪼개지 않았습니다.** 할당은 상태가 아니라 필드입니다
(`ticket_meta.assignee_id`). 상태로 만들면 진실이 두 군데 생기고 반드시
어긋납니다 — `status='할당완료'` 인데 `assignee_id` 가 null 인 티켓이
표현 가능해집니다. "분석은 끝났는데 담당자가 없는 건" 은 조회입니다:
`status = 'triage' and assignee_id is null`.

**보류(on_hold)를 넣었습니다.** 요청자를 기다리는 것은 액터도 대기 대상도
다릅니다. 그리고 이게 없으면 MTTR 이 거짓말을 합니다.

**'승인 대기' 는 넣지 않았습니다.** 기준상 자격은 있지만(관리자가 신규개발
승격을 판단), 승격 시점이 `promoted_at`/`promoted_by` 로 이미 남고 있어
조회로 뽑을 수 있습니다. 보드 열 하나를 더 쓸 값어치는 아니라고 봤습니다.
이건 명백한 답이 있는 게 아니라 보드 폭과 맞바꾼 판단입니다.

### 보류는 단계가 아니라 옆길

`STATUSES`(보드 열 순서, 7개)와 `PIPELINE_STATUSES`(순서 있는 단계, 6개)를
나눴습니다. 보류는 어느 단계에서든 들어갔다 **들어갈 때의 자리로만** 돌아옵니다.

돌아갈 자리를 아무 데나 허용하면 보류를 한 번 거치는 것만으로 팀원이 단계를
건너뛸 수 있고, 그러면 인접 이동 규칙이 있으나 마나입니다. 그래서 보류로
들어갈 때 트리거가 `hold_from_status` 에 직전 단계를 적습니다.

**이 규칙은 DB 가 막습니다** (`guard_status_transition()`). 지금까지 인접 이동
규칙은 웹에만 있었고 RLS 는 *누가* 고칠 수 있는지만 봤습니다. 보류를 넣으면
그 구멍이 커지므로 트리거로 옮겼습니다. 관리자와 `auth.uid()` 가 null 인
경로(에이전트, SQL Editor)는 통과합니다.

보류 사유는 CHECK 제약으로 강제합니다 — 관리자도 예외가 아닙니다.
사유 없는 보류는 왜 멈췄는지 아무도 모른 채 남습니다.

### 보류 시간과 지표

`ticket_lead_times` 뷰가 이력에서 보류 구간을 이어 붙여 계산합니다.

| 지표 | 보류를 빼는가 | 왜 |
|---|---|---|
| MTTA (접수→착수) | 착수 **전** 보류를 뺌 | 팀이 손 놓고 있던 시간이 아님 |
| MTTR (착수→완료) | 착수 **후** 보류를 뺌 | 요청자 회신 대기는 수리가 아님 |
| 리드타임 (접수→완료) | **안 뺌** | 요청자가 실제로 겪은 시간 |

구간이 착수 시각을 걸칠 수는 없습니다 — 착수하려면 상태가 바뀌어야 하고,
그 순간 보류 구간이 끝나기 때문입니다. 그래서 둘로 정확히 갈립니다.

로컬 PostgreSQL 16 에 스키마를 올려 시나리오로 검증했습니다:
보류 합계 28h, MTTA 3h(7h−4h), MTTR 16h(40h−24h), 리드타임 47h(안 뺌).

### 종료 방식에 기본값을 두지 않는 이유

접수 판정을 일부러 느슨하게 잡았으므로(놓치는 것보다 잘못 접수되는 게 낫다)
오접수는 반드시 들어옵니다. 그런데 반려할 방법이 삭제뿐이었고, 삭제하면
중복 판정 근거인 `tickets.source_message_id` 가 사라져 **다음 스캔에서 같은
메일이 다시 티켓이 됩니다.** 그래서 반려는 삭제가 아니라 종료 방식입니다.

`fixed` 를 기본값으로 두지 않습니다. 값이 없으면 '미지정' 이지 '고쳤음' 이
아닙니다. 옛 완료 건이 전부 null 이라 NOT NULL 제약도 걸 수 없고, 걸어서도
안 됩니다 — 없는 사실을 만들게 됩니다.

`rejected`/`duplicate`/`cancelled`/`wontfix` 는 통계 모수에서 뺍니다. 넣어 두면
"반려까지 3분" 같은 건이 평균을 끌어내려 지표가 실제보다 좋아 보입니다.
`wontfix` 도 뺍니다 — 검토는 했지만 수리는 안 했으므로 수리 시간이 없습니다.

### 라벨은 내부 영어, 외부 한국어

저장값은 원래부터 영어였고 한글이었던 건 화면 라벨뿐이라, 마이그레이션 없는
교체였습니다.

`triage` 를 '분석/할당' 두 단어로 붙여 놨던 것이 증상이었습니다 — 번역이
안 되는 단어를 억지로 옮긴 것입니다. 화면과 DB·로그가 같은 단어를 쓰면
옮겨 읽을 일이 없습니다.

**요청자에게 나가는 완료 회신 메일만 한국어로 남깁니다.** 받는 사람은
재무팀·물류팀·인사팀이지 IT 팀이 아니고, 그분들에게 'Deploy' 는 설명이
필요한 단어입니다. 웹은 `STATUS_LABELS_KO`, 에이전트는 `constants.py` 의
`STATUS_LABELS` 를 씁니다.

### 끌어서 옮기기는 보류·완료로 못 갑니다

보드에서 카드를 끌면 보류 사유나 종료 방식을 물어볼 자리가 없습니다.
그대로 두면 사유 없는 보류와 종료 방식 없는 완료가 쌓입니다. 그래서
보드에서는 막고 상세 화면으로 보냅니다.

## 11. 시스템 설정 — API 키를 화면에서 등록하기 (2026-08-06)

### 왜 app_settings 에 넣지 않았는가

`app_settings` 는 `settings_read` 정책이 `is_member()` 입니다 — **팀원 누구나
값을 읽습니다.** Gemini API 키를 거기 두면 로그인한 팀원 아무나 REST 로
긁어갈 수 있고, 그 키로 과금이 발생합니다.

그래서 `app_secrets` 를 따로 만들고 **정책을 하나도 만들지 않았습니다.**
RLS 가 켜져 있는데 정책이 없으면 anon·authenticated 는 전부 막힙니다.

거기에 더해 **GRANT 자체를 걷어냈습니다.** Supabase 는 public 스키마의 새 표에
anon·authenticated 권한을 자동으로 답니다. 그대로 두면 이 표를 막는 것이 RLS
하나뿐이 되고, 나중에 누가 정책을 하나 잘못 만드는 순간 뚫립니다.

### 접근 경로는 둘뿐

| 누가 | 어떻게 | 무엇을 |
|---|---|---|
| 에이전트 | service_role 키 (RLS 우회 + 명시적 GRANT) | 값을 읽습니다 |
| 웹 (관리자) | `set_app_secret` / `app_secret_status` 함수 | 넣을 수만 있습니다 |

**한 번 넣은 키는 화면으로 다시 꺼낼 수 없습니다.** 상태 조회 함수는 마지막
4글자만 돌려줍니다. 확인이 필요하면 확인하는 게 아니라 교체하는 것이 맞습니다.

로컬 PostgreSQL 16 에서 7가지를 확인했습니다:

| 상황 | 결과 |
|---|---|
| 관리자가 등록 | 통과 |
| 관리자가 상태 조회 | 마스킹된 힌트만 (`•••…9x7Q`) |
| 관리자가 표를 직접 select | `permission denied` |
| 팀원이 상태 조회 | `관리자만 볼 수 있습니다` |
| 팀원이 등록 시도 | `관리자만 등록할 수 있습니다` |
| 팀원이 표를 직접 select | `permission denied` |
| 비로그인(anon)이 함수 호출 | `permission denied for function` |
| 에이전트(service_role)가 값 읽기 | 읽힘 |

### 설정 화면이 .env 를 이깁니다

키가 있을 수 있는 곳이 두 군데(설정 화면, `.env`)이고 **설정 화면이 우선**입니다.

화면에서 등록·교체하는 목적 자체가 Windows PC 에 붙지 않고 키를 바꾸는 것인데,
`.env` 가 이기면 화면에서 바꿔도 아무 일이 일어나지 않습니다. 운영자는 바꿨다고
믿고 있는데 실제로는 옛 키가 계속 쓰입니다 — 조용히 틀리는 쪽이 가장 나쁩니다.

`.env` 는 대비책입니다. DB 에 등록하지 않았거나 지웠을 때 씁니다.

고르는 규칙은 `secrets.py` 의 `choose_gemini` 순수 함수입니다 — Supabase 없이
테스트할 수 있어야 해서 떼어 놓았습니다. 공백만 있는 값은 '없는 것' 으로 보고,
붙여넣을 때 딸려 오는 줄바꿈은 잘라냅니다.

어느 쪽을 쓰고 있는지는 `ticket-agent doctor` 가 마스킹한 형태로 알려 줍니다.
값 자체는 로그에도 남기지 않습니다.

## 12. 접수일을 고칠 수 있게 (2026-08-12)

`tickets.received_at` 은 처음부터 고정값이었습니다. 담당자가 제목·요청자·내용을
고칠 수 있게 된 뒤에도 접수일만은 `updateTicketFields` 에서 일부러 뺐습니다.
"받은 사실" 이라 판단의 대상이 아니고, 리드타임의 기준점이기 때문입니다.

### 왜 열었는가

받은 날과 접수로 쳐야 할 날이 다른 경우가 실제로 있습니다.

- 전화로 먼저 접수하고 메일은 며칠 뒤에 온 건
- 수동 등록에서 **등록 시각**이 그대로 접수일이 된 건
- 후속 메일이 새 티켓이 됐다가 원래 건으로 정리된 경우

여기서 접수일이 고정이면 리드타임·MTTA·MTTR·주간 집계가 통째로 틀린 채
굳습니다. 못 고치게 막는 것은 정확성을 지키는 게 아니라 **틀린 값을 보존하는
것**입니다. 고칠 수 있어야 맞출 수 있습니다.

권한은 다른 티켓 필드와 같습니다 — `can_edit_ticket`(담당자와 관리자).
접수일에만 관리자 잠금을 걸면 담당자가 자기 티켓의 리드타임이 틀린 것을 보고도
관리자를 기다려야 합니다.

### 미래만 막습니다

과거로 옮기는 것은 이 기능의 목적이라 막지 않습니다. 미래는 막습니다 —
미래 접수일은 모든 경과 시간을 음수로 만들고, `formatHours` 는 음수를 `-` 로
지웁니다. 틀렸다는 사실조차 화면에 안 남습니다.

규칙은 두 곳에 있고 내용이 같아야 합니다.

| 어디 | 무엇 |
|---|---|
| `workflow.ts` 의 `receivedAtError` | 저장 전에 막고 이유를 보여줍니다 (편의) |
| `guard_received_at()` 트리거 | 실제 차단. 화면을 거치지 않아도 막힙니다 |

시계 오차 5분은 봐 줍니다 (`RECEIVED_AT_SKEW_MINUTES` = `interval '5 minutes'`).
사용자 PC 가 몇 분 빠른 것은 오기가 아닙니다.

트리거는 **update 에서만** 봅니다. insert 까지 막으면 발신자 시계가 어긋난 메일
한 통 때문에 스크리닝의 '접수' 버튼이 통째로 실패합니다. 값이 바뀌지 않은
update 도 통과시킵니다 — 이미 미래로 적힌 옛 티켓의 제목조차 못 고치게 되면
고칠 길이 사라집니다.

### 고쳤다는 사실이 보여야 합니다

원본 메일 스냅숏(`scanned_mails.received_at`)은 그대로입니다. 티켓 접수일이
원본 수신일시와 다르면 '원본 메일 (증적)' 칸에 조정됐다고 적습니다 — 제목이
원본과 다를 때 이미 하고 있는 것과 같은 방식입니다. 리드타임이 왜 그 값인지를
나중에 설명할 수 있어야 합니다.

입력은 `datetime-local` 칸이라 로컬 시간을 다루고 DB 는 UTC 를 담습니다.
`toDateTimeInput`/`fromDateTimeInput` 이 짝으로 변환합니다 — 한쪽만 쓰면
시차만큼 어긋난 접수일이 조용히 저장됩니다.
