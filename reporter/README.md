# desk 수집기 · 월간 보고서 생성기

desk 를 주기적으로 떠서 **스냅샷을 쌓고 대시보드에 올립니다.** 그 위에 월간
보고서와 업무 전수 목록을 만듭니다.

> **주간 보고서는 여기 없습니다.** 이슈트래커의 `태스크맵` 화면에서 만듭니다
> (`web/src/lib/report/`). 집계 규칙을 두 벌 두면 갈라지기 때문에, 주간 쪽
> 코드는 통째로 그쪽으로 옮겼습니다. 이 도구가 할 일은 그 화면이 볼 스냅샷을
> 제때 올려 두는 것입니다.
서식은 `활동_월간요약보고서.pptx` (2026.07, PptxGenJS 생성 후 손질된 원본)를
역설계한 것입니다. 그 파일 자체는 저장소에 없고, **좌표는 `src/layout.ts` 에
상수로 옮겨져 있습니다** — 원본이 없어도 생성은 됩니다.

```
                                       ┌─→ 주간 diff ─→ out/주간업무보고_YYYY-Www.pptx
desk.saebom.me/api/state ─→ 태스크 맵 ─┤
                              ↑        ├─→ 집계 ────→ out/활동_월간요약보고서_YYYY-MM.pptx
티켓 대시보드 (Supabase) ─────┼────────┘              out/업무목록_YYYY-MM-DD.xlsx
                        config/taskmap.json
                        (npm run ui 로 편집)
```

## 설치

```bash
cd reporter
npm install
cp .env.example .env      # SUPABASE_EMAIL / SUPABASE_PASSWORD 를 채웁니다
```

Node 22 이상이 필요합니다 (`node:sqlite` 를 씁니다).

## 명령

```bash
npm run doctor            # 설정·연결·쿠키 만료 점검
npm run scan              # desk 를 읽어 스냅샷 저장 + 대시보드 업로드
npm run push              # 밀린 스냅샷·태스크 맵만 올리기
npm run monthly           # 지난달 보고서 생성
npm run monthly 2026-08   # 특정 달
npm run list              # 업무 전수 목록 xlsx (프로젝트별 · 담당자별)
npm run ui                # 태스크 맵 편집 화면 (127.0.0.1:4173)
npm test                  # 집계·레이아웃 165개 + 타입체크
```

터미널을 안 쓸 때는 **`start-reporter.command` 를 더블클릭**합니다. Node 버전과
`.env` 를 먼저 점검하고 의존성을 알아서 맞춘 뒤 위 명령을 메뉴로 물어봅니다.
보고서를 만들면 `out/` 폴더를 열어 줍니다. 정기 실행은 그대로 launchd 가 맡습니다 —
이 파일은 손으로 돌릴 때 쓰는 것이고, 둘은 같은 CLI 를 부릅니다.

## 왜 스냅샷을 쌓는가

**desk 는 현재 상태만 보관합니다.** 과거 이력이 없습니다.

| 알고 싶은 것 | 원본만으로 | 스냅샷이 쌓이면 |
|---|---|---|
| 일정이 밀렸는가 (`7/13 → 8/6`) | 불가능 (최초 마감일 필드가 없음) | 가능 |
| 이번 달에 새로 생긴 업무 | 불가능 | 가능 |
| 프로젝트 진척 증가분 | 불가능 | 가능 |

오늘 안 떠 놓으면 오늘의 상태는 영영 복원되지 않습니다.
**보고서를 안 만드는 달에도 `scan` 은 돌려야 합니다.**

## desk 인증 — 한 달에 한 번 사람이 합니다

desk 는 Cloudflare Access 뒤에 있고 Service Token 이 발급돼 있지 않습니다.
그래서 **Chrome 에 저장된 `CF_Authorization` 쿠키를 재사용**합니다.

- 쿠키는 macOS 키체인의 "Chrome Safe Storage" 키로 복호화합니다.
  최초 1회 접근 허용을 묻습니다.
- Chrome 이 켜져 있어도 됩니다 (DB 를 복사한 뒤 읽습니다).
- 프로필을 지정하지 않으면 전부 훑어 **만료가 가장 늦은** 쿠키를 씁니다.
- 세션은 한 달입니다. `scan`·`doctor` 가 남은 일수를 매번 찍고,
  7일 이하로 남으면 경고합니다.

만료되면 Chrome 으로 desk 에 로그인하면 끝입니다. 자동 추출이 깨진 경우에는
`.env` 의 `CF_AUTHORIZATION` 에 값을 직접 넣습니다 — 이 값이 자동 추출을 이깁니다.

> 쿠키가 이 Mac 의 Chrome 에 묶여 있으므로 **GitHub Actions 로 옮길 수 없습니다.**
> Cloudflare Service Token 을 발급받으면 그때 재검토합니다.

## 대시보드 접근

Publishable(anon) 키로 **로그인해서** 읽고 씁니다. RLS 가 그대로 살아 있습니다.
`service_role` 키는 쓰지 않습니다 — 그 키는 에이전트 PC 의 `.env` 한 곳에만
있어야 합니다.

### 스냅샷을 대시보드로 올립니다

`scan` 이 끝나면 **로컬에 있는데 대시보드에 없는 날짜만** 올립니다
(`desk_snapshots` · `task_map`, `supabase/schema.sql` 24장). 이미 올린 것을 매번
다시 올리면 스냅샷 하나가 수백 KB 라 스캔마다 몇 MB 를 왕복합니다.

**업로드가 실패해도 스캔은 성공입니다.** 스냅샷은 로컬에 남아 있고 나중에
`npm run push` 로 올리면 됩니다. 여기서 멈추면 그날 수집까지 실패한 것처럼
보이는데, 스냅샷은 놓치면 복원이 안 되는 쪽이라 그렇게 두면 안 됩니다.

> 표를 아직 안 만들었으면 `Could not find the table 'public.desk_snapshots'` 가
> 납니다. Supabase SQL Editor 에서 `supabase/schema.sql` 을 다시 실행하세요
> (한 파일이고 재실행해도 안전합니다).

쓰기는 **관리자 계정만** 통과합니다. 스냅샷은 그 Mac 한 대만 올리면 되고,
태스크 맵은 팀 전체 보고서의 모양을 바꾸는 규칙이라 아무나 고치면 매주 다른
보고서가 나갑니다.

**대분류 3종을 전부 읽습니다** — `ticket_meta.work_type` 의 `incident`(장애) ·
`maintenance`(유지보수) · `development`(신규개발). `category`(오류·개선·수정·신규)
가 아닙니다. 대분류가 유지보수인 것과 중분류가 개선인 것은 다른 축입니다.

> 처음에는 조회 단계에서 `work_type='incident'` 로 걸러 장애만 받았습니다.
> 기획서(`docs/reference/SPEC-REPORTER.md` 7.2)가 2장을 "장애 발생 추이"로
> 정해 뒀기 때문입니다. 실제로 돌려 보니 대시보드의 6건이 **유지보수 5 ·
> 신규개발 1 · 장애 0** 이라 보고서의 2장이 통째로 0 이었습니다. 한 일이 있는데
> 없다고 적히는 것이라, 2장을 **운영 현황**으로 넓혔습니다. 기획서와 다른
> 지점이고, 넓힌 쪽이 맞습니다.

## 월간 집계 규칙

전부 `src/aggregate.ts` 의 순수 함수입니다 (주간은 `src/weekly.ts`).
렌더링 코드에서 계산하지 않습니다.

| 항목 | 규칙 |
|---|---|
| 완료 | `status = 'done'` 이고 `completedOn` 이 그 달 |
| 지연 | 미완료 + 마감일 있음 + 마감일 < 월말 |
| 진행중 | 그 외 |
| 표 묶음 | **프로젝트**별. 그 달 업무가 없는 프로젝트는 안 그립니다 |
| 묶음 정렬 | 지연 있는 것 → 업무 많은 것, 미지정은 맨 뒤 |
| 묶음 안 정렬 | 지연 → 완료 → 진행중 |
| 묶음 진척율 | 프로젝트 마일스톤 `done/total` |
| 업무 행 진척율 | 완료 100%, 그 외는 **비웁니다** |
| 당월 운영 건수 | 대분류별. `work_type` 이 셋 중 하나가 아니면 **어디에도 안 셉니다** |
| 전월 대비 | 대분류 3종 **합계** 기준 |
| 추이 막대 | 장애·유지보수 2계열. 신규개발은 카드에만 (아래 참조) |
| 장애 등급 | `critical`→매우심각, `high`→심각, `medium`·`low`→보통 |
| 등급 모수 | **장애만.** 유지보수 티켓의 `severity` 는 세지 않습니다 |

### 왜 시스템이 아니라 프로젝트로 묶는가

desk 는 시스템(운영 대상)과 프로젝트(구축 작업)를 별개 축으로 둡니다.
연결률이 갈랐습니다 — 실측 `work.system` **19/38**, `work.project` **26/38**.
시스템으로 묶으면 절반이 '미지정' 으로 가고, 등록된 시스템 11개 중 5개는
연결된 업무가 아예 0건입니다. 프로젝트에는 마일스톤이 있어 묶음 진척율까지
나옵니다.

### 지면이 모자랄 때

표 영역은 3.20인치로 고정입니다. 묶음 머리행(0.20)과 업무 행(0.26)을
**인치 단위로** 계산해 들어가는 만큼만 넣습니다 (`fitGroups`).

1. **머리행을 업무 행보다 우선합니다.** 프로젝트 목록 자체가 개발현황이고,
   머리행에 완료·진행·지연 건수와 진척율이 있어 업무 행이 없어도 뜻이 통합니다.
2. **남는 높이는 라운드로빈으로 나눕니다.** 앞에서부터 채우면 첫 프로젝트가
   남은 높이를 다 먹고 뒤쪽은 업무가 한 건도 안 보입니다.

머리행의 건수는 **자르기 전 전체**이므로 행이 접혀도 몇 건이었는지는
사라지지 않고, 접힌 건수는 꼬리말에 적힙니다.

## 주간 업무 보고는 이슈트래커에서

`week`·`weekly`·`milestones`·`layout`·`draw`·`weeklyRender` 가
`web/src/lib/report/` 로 옮겨 갔습니다. 규칙(화~월 구간, 완료는 스냅샷 전이로
판정, 보류는 이슈 절로, 마일스톤 레일)은 그대로이고 자리만 바뀌었습니다.

**두 벌로 두지 않은 이유**는 집계 규칙이 갈라지면 어느 쪽 숫자가 맞는지 아무도
모르게 되기 때문입니다. 이 저장소는 이미 코드값을 세 곳에 두는 부담을 지고
있습니다 (`CLAUDE.md`) — 거기에 집계까지 얹지 않습니다.

### 업무 목록(xlsx)은 보고서와 규칙이 다릅니다

`npm run list` 는 pptx 와 **같은 스냅샷을 보되 다르게 다룹니다.**

| | 월간 보고서(pptx) | 업무 목록(xlsx) |
|---|---|---|
| 범위 | 그 달에 일어난 일만 | 스냅샷의 **전부** |
| 지면 | 3.20인치에 맞춰 자름 | 자르지 않음 |
| 빈 프로젝트 | 안 그림 | **남김** ("등록된 업무 0건"도 사실입니다) |
| 프로젝트 없는 업무 | 미지정 묶음(맨 뒤) | **기타** 에 개별 항목으로 |
| 담당자 | 열 하나 | 프로젝트 안에서 사람별로 묶고 반복은 생략 |

보고서에서 지면 때문에 접힌 건을 확인하는 자리입니다. 시트는 셋 —
`업무 목록`(전수) · `인원별 요약` · `프로젝트별 요약`.

**지연은 완료·진행중·대기와 별개 축입니다.** 상태 셋은 합쳐 전체가 되지만
지연은 미완료 건에 붙는 표시라 네 번째 상태가 아닙니다. 나란히 놓으면 넷을
더해 보게 되므로 요약 시트마다 그 사실을 한 줄로 적습니다.

**진척율(%)은 세 자리에 나오고 셋의 뜻이 다릅니다.** 같은 이름으로 뭉뚱그리면
프로젝트 수치가 개인 실적처럼 읽힙니다.

| 자리 | 값 | 근거 |
|---|---|---|
| 프로젝트 머리행 · 프로젝트별 요약 | 진척율 | 완료 마일스톤 ÷ 전체 마일스톤 |
| 업무 행 | 진척율 | 완료는 100%, 그 외는 desk `work.progress` |
| 인원별 요약 | **완료율** | 완료 ÷ 전체 건수 |

인원 칸만 이름이 다릅니다. desk 에 사람 단위 진척 값이 없고 업무마다 크기가
제각각이라 '완료 3/9' 가 일의 3분의 1을 뜻하지 않기 때문입니다 — 진척율이라고
쓰면 그렇게 읽힙니다. 시트 아래에도 같은 문장을 적어 둡니다.

셀은 **문자열이 아니라 숫자 + `0%` 서식**입니다. 문자열이면 정렬했을 때 100% 가
44% 앞에 오고 평균도 못 냅니다. 값이 없으면 0% 가 아니라 **빈 칸**입니다 —
`work.progress` 는 실측 38건 전부 비어 있어서 지금은 완료 건만 100% 로 찹니다.

### 왜 추이는 2계열인가

한 달 슬롯의 폭이 0.30인치입니다 (원본 실측치). 둘로 쪼개면 0.14 + 간격 0.02 +
0.14 로 높이 비교가 되지만, 셋으로 쪼개면 막대 하나가 0.09인치가 되어 색만 보이고
길이가 안 읽힙니다. 그래서 막대는 **장애·유지보수**만 그리고 신규개발은 당월
카드에 둡니다. 그 달에 신규개발이 실제로 있었으면 각주에 적습니다 —
안 적으면 막대 두 개의 합이 그 달 총건수로 읽힙니다.

값 라벨은 **당월 슬롯에만** 붙입니다. 2계열 × 7개월 = 막대 14개이고, 차트 규칙이
"항목 10개 이하일 때만 모든 막대에 값"입니다. 과거 달은 높이로 읽습니다.

### 지어내지 않는 것

- **마감일 없는 업무를 지연으로 몰지 않습니다.** desk 실측 38건 중 17건이
  마감일 없음입니다. 이걸 지연으로 세면 매달 빨간 표시가 절반을 넘고
  읽는 사람이 지연 표시를 무시하게 됩니다. 일정 칸에 `(계획)` 이라고 적습니다.
- **`work.progress` 는 38건 전부 비어 있습니다.** 업무 단위 진척율을 만들 근거가
  없어 미완료 업무 행의 진척율 칸은 비웁니다. 프로젝트 진척율은 묶음 머리행에만
  나옵니다 — 업무 행에 찍으면 프로젝트 수치가 업무 수치처럼 읽힙니다.
- **`assessment` 는 38건 전부, `detail.notes` 는 6건만 있습니다.**
  '주요 진행 내용' 칸이 비는 것은 버그가 아니라 desk 에 기록이 없는 것입니다.
  제목을 베껴 채우지 않습니다.
- **집계 시작 이전 달을 0 으로 채우지 않습니다.** "0건" 과 "집계 전" 은
  다른 사실입니다. 막대를 안 그리고 몇 개월치인지 각주에 적습니다.
- **대분류를 모르는 티켓을 유지보수로 밀어 넣지 않습니다.** DB 기본값이
  `maintenance` 이지만, 그걸 집계에서 되풀이하면 대시보드에 없던 유지보수 건이
  보고서에서 생겨납니다. 어느 칸에도 안 세고 각주에 `대분류 미상 N건 제외`.
- **표에서 잘라낸 행은 반드시 꼬리말에 적습니다.** 조용히 자르면 19건짜리
  달이 9건짜리로 보입니다.

## 주기 실행 (launchd)

`scripts/me.saebom.reporter.plist` 를 복사해 등록합니다.

```bash
cp scripts/me.saebom.reporter.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/me.saebom.reporter.plist
```

월요일 18:00 `scan`(구간 마감 상태), 화요일 09:00 `scan`, 매월 1일 09:30 에
지난달 `monthly` 를 돌립니다.

주간 구간이 화~월이라 **월요일이 끝나야 그 주가 닫힙니다.** 월요일 저녁 스캔이
구간 마감 상태를 담고, 화요일 아침 스캔이 그것을 대시보드에 올립니다. 보고서
자체는 이슈트래커에서 사람이 만듭니다.
로그는 `data/reporter.log` 에 쌓입니다.

> 노트북이 잠들어 있으면 launchd 는 **깨어난 직후** 밀린 작업을 한 번 돌립니다.
> 주 1회 스캔을 놓쳐도 다음 스캔이 2주치를 한 번에 잡지만, 그 사이의 변화는
> 뭉뚱그려집니다.
