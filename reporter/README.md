# 주간·월간 업무 보고서 생성기

desk 와 티켓 대시보드에서 자료를 모아 **한 장짜리 pptx** 를 만듭니다.
보고서는 두 종류입니다 — **주간 업무 보고**(지난주 대비 변화)와
**활동 월간 요약 보고서**(그 달의 상태). 서식·좌표는 하나를 같이 씁니다.
서식은 `활동_월간요약보고서.pptx` (2026.07, PptxGenJS 생성 후 손질된 원본)를
역설계한 것입니다. 그 파일 자체는 저장소에 없고, **좌표는 `src/layout.ts` 에
상수로 옮겨져 있습니다** — 원본이 없어도 생성은 됩니다.

```
                                       ┌─→ 주간 diff ─→ out/주간업무보고_YYYY-Www.pptx
desk.saebom.me/api/state ─→ 태스크 맵 ─┤
                              ↑        ├─→ 집계 ────→ out/활동_월간요약보고서_YYYY-MM.pptx
티켓 대시보드 (Supabase) ─────┼────────┘              out/업무목록_YYYY-MM-DD.xlsx
                        config/taskmap.json
                        (npm run ui 로 편집)
```

## 설치

```bash
cd reporter
npm install
cp .env.example .env      # SUPABASE_EMAIL / SUPABASE_PASSWORD 를 채웁니다
```

Node 22 이상이 필요합니다 (`node:sqlite` 를 씁니다).

## 명령

```bash
npm run doctor            # 설정·연결·쿠키 만료 점검
npm run scan              # desk 를 읽어 오늘자 스냅샷 저장
npm run weekly            # 주간 업무 보고 (기본: 방금 끝난 화~월 구간)
npm run weekly 2026-08-10 # 특정 주 — 끝나는 **월요일**로 지정
npm run monthly           # 지난달 보고서 생성
npm run monthly 2026-08   # 특정 달
npm run list              # 업무 전수 목록 xlsx (프로젝트별 · 담당자별)
npm run ui                # 태스크 맵 편집 화면 (127.0.0.1:4173)
npm test                  # 집계·레이아웃 225개 + 타입체크
```

터미널을 안 쓸 때는 **`start-reporter.command` 를 더블클릭**합니다. Node 버전과
`.env` 를 먼저 점검하고 의존성을 알아서 맞춘 뒤 위 명령을 메뉴로 물어봅니다.
보고서를 만들면 `out/` 폴더를 열어 줍니다. 정기 실행은 그대로 launchd 가 맡습니다 —
이 파일은 손으로 돌릴 때 쓰는 것이고, 둘은 같은 CLI 를 부릅니다.

## 왜 스냅샷을 쌓는가

**desk 는 현재 상태만 보관합니다.** 과거 이력이 없습니다.

| 알고 싶은 것 | 원본만으로 | 스냅샷이 쌓이면 |
|---|---|---|
| 일정이 밀렸는가 (`7/13 → 8/6`) | 불가능 (최초 마감일 필드가 없음) | 가능 |
| 이번 달에 새로 생긴 업무 | 불가능 | 가능 |
| 프로젝트 진척 증가분 | 불가능 | 가능 |

오늘 안 떠 놓으면 오늘의 상태는 영영 복원되지 않습니다.
**보고서를 안 만드는 달에도 `scan` 은 돌려야 합니다.**

## desk 인증 — 한 달에 한 번 사람이 합니다

desk 는 Cloudflare Access 뒤에 있고 Service Token 이 발급돼 있지 않습니다.
그래서 **Chrome 에 저장된 `CF_Authorization` 쿠키를 재사용**합니다.

- 쿠키는 macOS 키체인의 "Chrome Safe Storage" 키로 복호화합니다.
  최초 1회 접근 허용을 묻습니다.
- Chrome 이 켜져 있어도 됩니다 (DB 를 복사한 뒤 읽습니다).
- 프로필을 지정하지 않으면 전부 훑어 **만료가 가장 늦은** 쿠키를 씁니다.
- 세션은 한 달입니다. `scan`·`doctor` 가 남은 일수를 매번 찍고,
  7일 이하로 남으면 경고합니다.

만료되면 Chrome 으로 desk 에 로그인하면 끝입니다. 자동 추출이 깨진 경우에는
`.env` 의 `CF_AUTHORIZATION` 에 값을 직접 넣습니다 — 이 값이 자동 추출을 이깁니다.

> 쿠키가 이 Mac 의 Chrome 에 묶여 있으므로 **GitHub Actions 로 옮길 수 없습니다.**
> Cloudflare Service Token 을 발급받으면 그때 재검토합니다.

## 대시보드 접근

Publishable(anon) 키로 **로그인해서** 읽습니다. RLS 가 그대로 살아 있습니다.
`service_role` 키는 쓰지 않습니다 — 그 키는 에이전트 PC 의 `.env` 한 곳에만
있어야 합니다.

**대분류 3종을 전부 읽습니다** — `ticket_meta.work_type` 의 `incident`(장애) ·
`maintenance`(유지보수) · `development`(신규개발). `category`(오류·개선·수정·신규)
가 아닙니다. 대분류가 유지보수인 것과 중분류가 개선인 것은 다른 축입니다.

> 처음에는 조회 단계에서 `work_type='incident'` 로 걸러 장애만 받았습니다.
> 기획서(`docs/reference/SPEC-REPORTER.md` 7.2)가 2장을 "장애 발생 추이"로
> 정해 뒀기 때문입니다. 실제로 돌려 보니 대시보드의 6건이 **유지보수 5 ·
> 신규개발 1 · 장애 0** 이라 보고서의 2장이 통째로 0 이었습니다. 한 일이 있는데
> 없다고 적히는 것이라, 2장을 **운영 현황**으로 넓혔습니다. 기획서와 다른
> 지점이고, 넓힌 쪽이 맞습니다.

## 월간 집계 규칙

전부 `src/aggregate.ts` 의 순수 함수입니다 (주간은 `src/weekly.ts`).
렌더링 코드에서 계산하지 않습니다.

| 항목 | 규칙 |
|---|---|
| 완료 | `status = 'done'` 이고 `completedOn` 이 그 달 |
| 지연 | 미완료 + 마감일 있음 + 마감일 < 월말 |
| 진행중 | 그 외 |
| 표 묶음 | **프로젝트**별. 그 달 업무가 없는 프로젝트는 안 그립니다 |
| 묶음 정렬 | 지연 있는 것 → 업무 많은 것, 미지정은 맨 뒤 |
| 묶음 안 정렬 | 지연 → 완료 → 진행중 |
| 묶음 진척율 | 프로젝트 마일스톤 `done/total` |
| 업무 행 진척율 | 완료 100%, 그 외는 **비웁니다** |
| 당월 운영 건수 | 대분류별. `work_type` 이 셋 중 하나가 아니면 **어디에도 안 셉니다** |
| 전월 대비 | 대분류 3종 **합계** 기준 |
| 추이 막대 | 장애·유지보수 2계열. 신규개발은 카드에만 (아래 참조) |
| 장애 등급 | `critical`→매우심각, `high`→심각, `medium`·`low`→보통 |
| 등급 모수 | **장애만.** 유지보수 티켓의 `severity` 는 세지 않습니다 |

### 왜 시스템이 아니라 프로젝트로 묶는가

desk 는 시스템(운영 대상)과 프로젝트(구축 작업)를 별개 축으로 둡니다.
연결률이 갈랐습니다 — 실측 `work.system` **19/38**, `work.project` **26/38**.
시스템으로 묶으면 절반이 '미지정' 으로 가고, 등록된 시스템 11개 중 5개는
연결된 업무가 아예 0건입니다. 프로젝트에는 마일스톤이 있어 묶음 진척율까지
나옵니다.

### 지면이 모자랄 때

표 영역은 3.20인치로 고정입니다. 묶음 머리행(0.20)과 업무 행(0.26)을
**인치 단위로** 계산해 들어가는 만큼만 넣습니다 (`fitGroups`).

1. **머리행을 업무 행보다 우선합니다.** 프로젝트 목록 자체가 개발현황이고,
   머리행에 완료·진행·지연 건수와 진척율이 있어 업무 행이 없어도 뜻이 통합니다.
2. **남는 높이는 라운드로빈으로 나눕니다.** 앞에서부터 채우면 첫 프로젝트가
   남은 높이를 다 먹고 뒤쪽은 업무가 한 건도 안 보입니다.

머리행의 건수는 **자르기 전 전체**이므로 행이 접혀도 몇 건이었는지는
사라지지 않고, 접힌 건수는 꼬리말에 적힙니다.

## 주간 업무 보고

### 구간은 화요일 ~ 그다음 월요일입니다

보고서를 월요일이 끝난 뒤에 쓰기 때문입니다. 기본값은 **방금 끝난 구간** —
가장 최근 월요일(당일 포함)로 끝나는 7일입니다. 8/13(목)에 뽑으면
`8/4(화) ~ 8/10(월)` 이고, 파일명은 끝나는 월요일을 씁니다
(`주간업무보고_2026-08-10.pptx`).

> ISO 주차(월~일, `2026-W33`)를 쓰다 옮겼습니다. 팀 보고 주기가 화~월이라
> 하루씩 어긋났습니다. **주차 번호를 안 쓰는 이유**는 화~월 구간이 ISO 주차
> 두 개에 걸쳐 있어서, 번호를 붙이면 어느 쪽이든 거짓말이 되기 때문입니다.

**그 주의 상태는 구간이 끝난 뒤 처음 뜬 스냅샷**으로 봅니다. 늘 최신 스냅샷을
쓰면 2주 전 주간보고를 뒤늦게 뽑을 때 그때가 아니라 오늘 상태로 보고하게 됩니다.
구간 마감 뒤 스냅샷이 아직 없으면 최신 것을 쓰고 그 사실을 각주에 적습니다.

월간은 그대로 **1일 ~ 말일**입니다.

### 무엇을 대조하는가

`npm run weekly` 는 **스냅샷 두 개를 대조**합니다. 월간이 '그 달의 상태' 를 찍는
문서라면 주간은 '지난주 대비 무엇이 달라졌는가' 가 본문입니다.

| 구성 | 내용 |
|---|---|
| 요약 띠 | 금주 완료 · 착수 · 신규 · 진행 · 지연 + 비교에 쓴 스냅샷 날짜 |
| 1장 | **프로젝트 → 하위 태스크** 표. 담당자·상태·진척율·일정 |
| 2장 | 프로젝트별 진척 (지난주 → 이번주, 마일스톤 증가분) |
| 3장 | 이슈 — 일정 변경 · 보류 · 지연 · 정체 |
| 4장 | 차주 마감인 미완료 업무 |

**슬라이드는 두 장**입니다. 첫 장이 위 넷이고, 둘째 장이 아래 프로젝트 진행 레일입니다.

### 둘째 장 — 프로젝트 진행

desk `Weekly Report` 의 `1 프로젝트 진행 · 마일스톤` 을 옮겼습니다.
**일정표가 아니라 각 프로젝트가 지금 어디까지 왔는지를 보는 장**이라,
날짜보다 칩의 위치가 본문입니다.

```
글로벌 BRS — 홍콩   4/9  ✓국가별 확장성 설계 ─ … ─ [구현 ~7/29] ─ 배포 ─ 테스트   목표 8/31
결제 시스템 구축 [보류] 8/9  ✓… ─ [배포 ~8/7]                                   목표 8/7
```

| 무엇 | 어디서 |
|---|---|
| 마일스톤 이름·완료여부·`4/9` | `project.milestones` 있는 그대로 |
| `보류` 배지 | `project.hold` 있는 그대로 (행 전체를 연하게) |
| 목표일 | `project.due`. 없으면 `—`, 지났으면 붉게 |
| 현재 칩의 `~7/29` | **파생** — 그 프로젝트 미완료 업무의 최소 마감일 |

**칩 날짜만 파생값입니다.** desk 는 `/api/state` 한 곳만 쓰고 그 응답의 마일스톤은
`{name, done}` 뿐입니다. 미완료 업무의 최소 마감으로 계산하면 desk 화면과
일치했습니다(BRS 7/29 · 카보너스 관리자 8/20 · Mobile App 8/11). **파생값임을
꼬리말에 밝힙니다.**

지면이 모자라면 글자를 7.5 → 6.0pt 까지 줄이고, 그래도 넘치면 **완료된 앞쪽을
`✓4` 로 접습니다.** 현재 칩과 그 뒤는 절대 접지 않습니다 — 그게 이 장의
본문입니다. 접은 사실은 꼬리말에 적습니다.

### 보류는 표에 안 넣고 이슈로 올립니다

desk 의 업무 상태는 넷입니다 — `done` · `ing` · `todo` · **`hold`**.
보고서 표의 상태는 **완료 · 진행중 · 지연 셋**이고, **보류는 그 축이 아닙니다.**

보류를 진행중에 섞으면 멈춰 있는 일이 '일하고 있는 것' 으로 읽힙니다. 그렇다고
빼 버리면 멈췄다는 사실 자체가 사라집니다. 그래서 **표에서 빼고 3장 이슈 절로
올립니다** — 일정 변경 다음, 지연·정체보다 앞입니다. 사유를 아는 사람이 있고
누군가의 답을 기다리는 상태라 먼저 풀리기 때문입니다.

```
3. 이슈 — 일정 변경 · 보류 · 지연 · 정체
   결제 시스템 운영서버 배포   보류 · Jacqueline · 결제 시스템 구축
```

몇 건을 뺐는지는 각주에 적습니다 (`보류 1건은 표에서 빼고 3장에 실었습니다`).
월간 보고서도 같은 규칙입니다. **업무 전수 목록(xlsx)만 예외로 보류를 그대로
보여 줍니다** — 그건 아무것도 빼지 않는 문서입니다.

통합 항목은 **구성원이 전부 보류일 때만** 보류입니다. 하나라도 굴러가면 그 일은
굴러가는 것입니다.

### 변화 판정 (기획서 6.4)

| 분류 | 조건 |
|---|---|
| 신규 | 지난주 스냅샷에 없던 `work.id` |
| 완료 | `done` 이 아니었다가 `done` — **`completedOn` 이 아니라 전이가 근거** |
| 착수 | `todo` → `ing` |
| 일정변경 | `due` 가 달라짐 (양쪽 다 값이 있을 때만) |
| 진척 | 프로젝트 `milestones` 의 done 개수 증가 |
| 정체 | 3주 연속 `ing` 이면서 위 변화가 하나도 없음 |

완료를 `completedOn` 으로 세지 않는 이유는 그 값이 **사람이 적는 값**이기
때문입니다. 실측 38건 중에도 `done` 인데 완료일이 빈 건이 있고, 완료일을
기준으로 삼으면 그 업무는 **어느 주간 보고서에도 안 나옵니다.**

### 프로젝트가 없는 업무

**가짜 프로젝트로 묶지 않습니다.** 서로 상관없는 일을 '미지정' 한 덩어리로
만들면 같은 묶음에 속한 일처럼 읽힙니다. 표 아래쪽에 얇은 구분선을 하나 긋고
그 아래는 **한 건씩 독립 항목**으로 세웁니다 — 머리행도, 묶음 진척율도 없습니다.

### 비교 대상이 없을 때

첫 주차에는 diff 가 성립하지 않습니다. 그때는 **만들기를 거부하지 않고**
`기준 주차 — 비교 대상 없음` 이라고 요약 띠에 붉게 적은 뒤 현재 상태만 싣습니다.

**없는 스냅샷을 빈 스냅샷으로 취급하지 않습니다.** 그러면 38건 전부가 '금주 신규'
가 되어 첫 보고서가 통째로 거짓이 됩니다. 정체(3주 연속)도 스냅샷 3주치가
쌓이기 전에는 판정하지 않고, 못 잰다는 사실을 각주에 적습니다.

### 지연 기준일

주 마지막 날이 아니라 **스냅샷 날짜와 주말 중 이른 쪽**입니다. 주 마지막 날로
잡으면 수요일에 만든 보고서에서 금요일 마감 건이 지연으로 빨갛게 뜹니다.

## 태스크 맵 — 사람마다 다른 등록 기준을 맞춥니다

`npm run ui` → `http://127.0.0.1:4173`

**문제.** 한 사람은 '카보너스 관리자 서비스'를 분석·설계·구현 3건으로 등록하고,
다른 사람은 1건으로 등록합니다. 그대로 보고서에 실으면 같은 크기의 일이 3행과
1행으로 나오고, 1page 예산이 **등록 습관에 따라** 들쭉날쭉해집니다. 프로젝트에
안 붙은 태스크도 실측 38건 중 12건입니다.

**규칙은 `config/taskmap.json` 한 곳에 남습니다.** 매주 기계가 같게 적용하므로
보고서 포맷이 안 흔들립니다. `data/` 가 아니라 `config/` 인 이유는 이 파일이
사람이 분류한 자산이고 **다시 뽑을 수 없기 때문**입니다 (data 는 gitignore).

### 규칙은 한 종류입니다

보고 항목(entry) 하나가 desk 태스크 N개를 가집니다.

| 하고 싶은 것 | 쓰는 법 |
|---|---|
| 통합 | `members` 에 여러 개 |
| 프로젝트 재배정 | `members` 1개 + `project` 지정 |
| 명칭 변경 | `members` 1개 + `title` 지정 |
| 제외 | `hidden: true` — **각주에 건수가 남습니다** |

**한 태스크는 최대 한 항목에만 속합니다.** 둘에 걸치면 건수가 두 번 세어지고,
합계가 desk 와 안 맞는데 원인을 찾기 어렵습니다. 저장 단계에서 막습니다.

**제외도 항목입니다.** 태스크 한 건을 빼려면 목록의 `제외` 버튼을 누릅니다 —
구성원 하나짜리 숨김 항목이 만들어집니다. 별도의 제외 목록을 두지 않는 이유는
규칙이 두 갈래가 되면 서로 어긋나기 때문입니다. `되돌리기` 로 한 번에 풉니다.

### 항목 미지정 ≠ 프로젝트 미지정

**둘은 다른 축입니다.** '항목 미지정' 은 태스크 맵에 보고 항목을 아직 안 만들었다는
뜻이고, 프로젝트에 잘 붙어 있어도 여기 셉니다. 결함이 아니라 **원본 그대로 한 줄씩
나간다**는 뜻이라 그냥 둬도 됩니다. 여러 건을 한 줄로 합치거나 이름·프로젝트를
바꾸고 싶을 때만 항목을 만듭니다.

### 통합 항목의 파생값

| 값 | 규칙 |
|---|---|
| 상태 | **전부 done 이어야 완료.** 하나라도 진행중이면 진행중 |
| 진척율 | 완료 구성원 ÷ 전체 (`구성 2/3` 을 진행내용 칸에 함께 표기) |
| 마감 (보고서 표) | **아직 안 끝난 구성원 중 가장 이른 날** |
| 기간 (목록 화면) | 가장 이른 시작 ~ **가장 나중에 끝나는 날** |
| 시작 | 가장 이른 시작일 |
| 담당자 | 한 명이면 이름, 여럿이면 `Alexa 외 1` |
| 유형 | 구성원 types 합집합 |

**보고서 표의 마감과 목록 화면의 기간은 일부러 다른 값입니다.** 표는 지연을 감추지
않는 것이 목적이고, 목록은 '이 일이 언제 시작해서 언제 끝나는가' 를 보는 자리입니다.

마감을 '가장 늦은 날' 로 뒀다가 되돌렸습니다. 카보너스 3건을 묶으니 8/4 에 지난
마감이 8/20 마감에 가려져 **지연 3건이 2건으로 줄었습니다.** 통합은 표를 줄이려고
하는 것이지 늦은 일을 감추려는 게 아닙니다.

### 화면

목록은 **안건 · 담당 · 진척 · 시작 · 종료(예정) · 상태** 를 함께 보여 줍니다.
종료 칸은 완료된 건이면 **실제 완료일**(진하게), 아직이면 **마감일**(`~` + 연하게),
둘 다 없으면 `(계획)` 입니다.

- **1page 예산 게이지** — 표 3.20인치 중 지금 구성이 몇 인치인지 실시간 표시.
  편집하는 동안 보여야 다 만들고 나서 잘리지 않습니다 (저장 전에도 갱신됩니다)
- **항목 미지정 · 끊어진 참조 뱃지** — 항목을 안 만든 태스크와 desk 에서 사라진 참조
- **추천** — 제목 접두어와 유형으로 통합 후보를 제안합니다. 실측에서 4묶음이
  잡혔습니다 (카보너스 관리자 3건 · 결제 운영서버 2건 · FABB 2건 · PG사 화면 2건)

**추천을 자동 적용하지 않습니다.** `PG사 화면 기획`(Jacqueline)과 `PG사 화면 기획
리뷰`(Alexa)는 제목이 거의 같지만 담당자가 다릅니다 — 같은 일인지 아닌지는
데이터로 판별할 수 없습니다. 누르는 순간 규칙이 되고 다음 주부터 자동 적용됩니다.

### 지어내지 않는 것

- **원본 스냅샷을 고치지 않습니다.** 맵은 보고 단계에서만 얹는 얇은 층입니다
- **미분류를 버리지 않습니다.** 항목에 안 속한 태스크는 원본대로 보고서에 나가고
  건수가 각주에 남습니다
- **끊어진 참조를 조용히 지우지 않습니다.** desk 에서 id 가 바뀌면 UI 뱃지와
  보고서 각주에 뜹니다. 지우면 다음 주에 미분류로 되살아나고 이유를 모릅니다
- **구성원 프로젝트가 서로 다르면 임의로 고르지 않습니다.** 사람이 정합니다

### 업무 목록(xlsx)은 보고서와 규칙이 다릅니다

`npm run list` 는 pptx 와 **같은 스냅샷을 보되 다르게 다룹니다.**

| | 월간 보고서(pptx) | 업무 목록(xlsx) |
|---|---|---|
| 범위 | 그 달에 일어난 일만 | 스냅샷의 **전부** |
| 지면 | 3.20인치에 맞춰 자름 | 자르지 않음 |
| 빈 프로젝트 | 안 그림 | **남김** ("등록된 업무 0건"도 사실입니다) |
| 프로젝트 없는 업무 | 미지정 묶음(맨 뒤) | **기타** 에 개별 항목으로 |
| 담당자 | 열 하나 | 프로젝트 안에서 사람별로 묶고 반복은 생략 |

보고서에서 지면 때문에 접힌 건을 확인하는 자리입니다. 시트는 셋 —
`업무 목록`(전수) · `인원별 요약` · `프로젝트별 요약`.

**지연은 완료·진행중·대기와 별개 축입니다.** 상태 셋은 합쳐 전체가 되지만
지연은 미완료 건에 붙는 표시라 네 번째 상태가 아닙니다. 나란히 놓으면 넷을
더해 보게 되므로 요약 시트마다 그 사실을 한 줄로 적습니다.

**진척율(%)은 세 자리에 나오고 셋의 뜻이 다릅니다.** 같은 이름으로 뭉뚱그리면
프로젝트 수치가 개인 실적처럼 읽힙니다.

| 자리 | 값 | 근거 |
|---|---|---|
| 프로젝트 머리행 · 프로젝트별 요약 | 진척율 | 완료 마일스톤 ÷ 전체 마일스톤 |
| 업무 행 | 진척율 | 완료는 100%, 그 외는 desk `work.progress` |
| 인원별 요약 | **완료율** | 완료 ÷ 전체 건수 |

인원 칸만 이름이 다릅니다. desk 에 사람 단위 진척 값이 없고 업무마다 크기가
제각각이라 '완료 3/9' 가 일의 3분의 1을 뜻하지 않기 때문입니다 — 진척율이라고
쓰면 그렇게 읽힙니다. 시트 아래에도 같은 문장을 적어 둡니다.

셀은 **문자열이 아니라 숫자 + `0%` 서식**입니다. 문자열이면 정렬했을 때 100% 가
44% 앞에 오고 평균도 못 냅니다. 값이 없으면 0% 가 아니라 **빈 칸**입니다 —
`work.progress` 는 실측 38건 전부 비어 있어서 지금은 완료 건만 100% 로 찹니다.

### 왜 추이는 2계열인가

한 달 슬롯의 폭이 0.30인치입니다 (원본 실측치). 둘로 쪼개면 0.14 + 간격 0.02 +
0.14 로 높이 비교가 되지만, 셋으로 쪼개면 막대 하나가 0.09인치가 되어 색만 보이고
길이가 안 읽힙니다. 그래서 막대는 **장애·유지보수**만 그리고 신규개발은 당월
카드에 둡니다. 그 달에 신규개발이 실제로 있었으면 각주에 적습니다 —
안 적으면 막대 두 개의 합이 그 달 총건수로 읽힙니다.

값 라벨은 **당월 슬롯에만** 붙입니다. 2계열 × 7개월 = 막대 14개이고, 차트 규칙이
"항목 10개 이하일 때만 모든 막대에 값"입니다. 과거 달은 높이로 읽습니다.

### 지어내지 않는 것

- **마감일 없는 업무를 지연으로 몰지 않습니다.** desk 실측 38건 중 17건이
  마감일 없음입니다. 이걸 지연으로 세면 매달 빨간 표시가 절반을 넘고
  읽는 사람이 지연 표시를 무시하게 됩니다. 일정 칸에 `(계획)` 이라고 적습니다.
- **`work.progress` 는 38건 전부 비어 있습니다.** 업무 단위 진척율을 만들 근거가
  없어 미완료 업무 행의 진척율 칸은 비웁니다. 프로젝트 진척율은 묶음 머리행에만
  나옵니다 — 업무 행에 찍으면 프로젝트 수치가 업무 수치처럼 읽힙니다.
- **`assessment` 는 38건 전부, `detail.notes` 는 6건만 있습니다.**
  '주요 진행 내용' 칸이 비는 것은 버그가 아니라 desk 에 기록이 없는 것입니다.
  제목을 베껴 채우지 않습니다.
- **집계 시작 이전 달을 0 으로 채우지 않습니다.** "0건" 과 "집계 전" 은
  다른 사실입니다. 막대를 안 그리고 몇 개월치인지 각주에 적습니다.
- **대분류를 모르는 티켓을 유지보수로 밀어 넣지 않습니다.** DB 기본값이
  `maintenance` 이지만, 그걸 집계에서 되풀이하면 대시보드에 없던 유지보수 건이
  보고서에서 생겨납니다. 어느 칸에도 안 세고 각주에 `대분류 미상 N건 제외`.
- **표에서 잘라낸 행은 반드시 꼬리말에 적습니다.** 조용히 자르면 19건짜리
  달이 9건짜리로 보입니다.

## 주기 실행 (launchd)

`scripts/me.saebom.reporter.plist` 를 복사해 등록합니다.

```bash
cp scripts/me.saebom.reporter.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/me.saebom.reporter.plist
```

월요일 18:00 `scan`(구간 마감 상태), 화요일 09:00 `scan` → `weekly`,
매월 1일 09:30 에 지난달 `monthly` 를 돌립니다.

주간 구간이 화~월이라 **월요일이 끝나야 그 주가 닫힙니다.** 월요일에 주간보고를
돌리면 아직 안 끝난 주를 보고하거나 한 주 전 것을 보고하게 됩니다.
로그는 `data/reporter.log` 에 쌓입니다.

> 노트북이 잠들어 있으면 launchd 는 **깨어난 직후** 밀린 작업을 한 번 돌립니다.
> 주 1회 스캔을 놓쳐도 다음 스캔이 2주치를 한 번에 잡지만, 그 사이의 변화는
> 뭉뚱그려집니다.

## 서식을 고칠 때

`layout.ts` 의 값은 원본에서 뽑은 실측치입니다. 임의로 바꾸지 마세요.
`tests/layout.test.ts` 가 슬라이드 경계와 칸 겹침을 검사합니다 —
오른쪽 단 장 제목 폭을 왼쪽과 같이 뒀다가 슬라이드 밖으로 나간 적이 있고,
파워포인트는 그것을 알려 주지 않고 그냥 잘라 그립니다.
